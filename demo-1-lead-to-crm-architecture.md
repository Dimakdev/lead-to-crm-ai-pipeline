# Демо-кейс №1 — Lead → CRM AI-пайплайн (універсальний B2B + B2C)

Версія 0.1 · 2026-09-14 · для збірки в n8n (self-hosted, Railway) + Airtable

---

## 1. Що доводить кейс

Що вхідний лід за 30 секунд перетворюється на оцінений рядок у CRM і готову чернетку відповіді, без ручного перенесення і без ручного сортування. І що система не падає, коли зовнішній сервіс віддає помилку.

Що кейс НЕ заявляє: написання CRM з нуля, ML-моделі, кастомний бекенд. Це workflow automation + AI-інтеграція.

---

## 2. Головне архітектурне рішення

Один воркфлоу, три гілки обробки, **один спільний контракт виходу**.

Розвилка йде не за словом «B2B / B2C», а за тим, скільки даних реально прийшло:

| Тип | Ознака | Хто оцінює |
|---|---|---|
| `thin` | є тільки контакт + канал + час | правило, ШІ не викликається |
| `thin_comment` | є короткий коментар або текст заявки | ШІ, одна вузька задача: теплота + намір |
| `rich` | є компанія або корпоративний домен | ШІ, повна кваліфікація + чернетка |

Усі три гілки віддають однаковий JSON. Тому далі — одна таблиця, одна маршрутизація, одне відео.

Принцип, який проговорюємо і в кейсі, і на дзвінку: **модель робить одне вузьке судження, все інше робить n8n**. Тригери, ретраї, credentials, історія прогонів — це робота движка, не моделі.

### Канонічний об'єкт

Все, що приходить з будь-якого джерела, зводиться до цього. Це контракт входу:

```json
{
  "source_channel": "form_site",
  "received_at": "2026-09-14T10:02:00Z",
  "name": "",
  "email": "",
  "phone": "",
  "company": "",
  "domain": "",
  "message": "",
  "raw": {}
}
```

Обов'язкові: `source_channel`, `received_at` і хоча б один з `email` / `phone`. Решта може бути порожньою — лід просто стане `thin`.

### Мапа джерел

Нормалізація не містить if/else по каналах. Вона читає одну мапу:

```js
const SOURCES = {
  form_site:    { weight: 45, map: { name: 'name', email: 'email', message: 'comment' } },
  referral:     { weight: 60, map: { name: 'full_name', phone: 'tel' } },
  email_inbound:{ weight: 45, map: { name: 'from_name', email: 'from', message: 'body' } },
  // додати свій канал: один запис тут + свій тригер на вхід ноди [2]
};
```

Новий канал = один запис у мапі + тригер. Ланцюг далі не змінюється. Над нодою `[2]` у графі стоїть sticky note: `Add your source here → map to canonical fields`.

## 3. Контракт виходу (єдиний для всіх гілок)

```json
{
  "score": 0,
  "heat": "hot | warm | cold",
  "category": "string",
  "reason": "string, до 200 знаків",
  "draft": "string, може бути порожній",
  "needs_review": false
}
```

Правила:
- поля обов'язкові всі, навіть якщо порожні;
- `reason` пишеться людською мовою, це те, що менеджер читає в CRM;
- `draft` для `thin` завжди порожній — там шаблонна відповідь, а не персональна;
- `needs_review: true` ставиться, коли валідація не пройшла або збагачення впало.

## 4. Схема даних в Airtable

### Таблиця `Leads`

| Поле | Тип | Нотатки |
|---|---|---|
| lead_id | Autonumber | |
| created_at | Date+time | час першого звернення |
| updated_at | Date+time | |
| source_channel | Single select | form_site, referral, ads_meta, ads_google, email_inbound, phone |
| lead_type | Single select | thin, thin_comment, rich |
| name | Text | |
| email | Email | |
| phone | Phone | |
| company | Text | порожнє для B2C |
| domain | Text | порожнє для B2C |
| message | Long text | коментар до заявки |
| enrichment | Long text | що вдалось дізнатись про компанію |
| score | Number | 0-100 |
| heat | Single select | hot, warm, cold |
| category | Single select | |
| reason | Long text | обґрунтування балу |
| draft | Long text | чернетка відповіді |
| status | Single select | New, Hot, Nurture, Contacted, Archived |
| touches | Number | скільки разів звертався |
| dedupe_key | Text | нормалізований email або телефон |
| needs_review | Checkbox | |
| run_id | Text | зв'язок з логом |

### Таблиця `Runs` (лог прогонів)

run_id · timestamp · trigger_source · lead_ref · status (ok / retry / error) · failed_node · error_message · duration_ms

Лог пишеться **завжди**, і на успіху, і на помилці. Це половина того, що продає кейс.

## 5. Ланцюг по нодах

```
[1] Тригери (два входи)
     ├─ Form Trigger (демо-форма)
     └─ Gmail Trigger (вхідний лист)
                │
[2] Normalize (Code)
     канонічний об'єкт + dedupe_key + lead_type
                │
[3] Airtable: Search by dedupe_key
     ├─ знайдено  → touches +1, гілка update
     └─ не знайдено → гілка create
                │
[4] Switch за lead_type
     ├─ thin         → [5a] Rule scoring (Code)
     ├─ thin_comment → [5b] Claude: heat + intent
     └─ rich         → [5c] Enrichment (HTTP) → Claude: повна кваліфікація + draft
                │
[6] Validate contract (Code)
     ├─ ok        → далі
     ├─ fail 1-2  → retry з жорсткішим промтом
     └─ fail 3    → fallback: score 50, heat warm, needs_review = true
                │
[7] Airtable: upsert у Leads
                │
[8] Switch за heat
     ├─ hot   → Telegram-алерт + Gmail draft (НЕ надсилається)
     ├─ warm  → Gmail draft + статус Nurture
     └─ cold  → шаблонна автовідповідь + Archived
                │
[9] Airtable: запис у Runs
```

Поверх усього: **Error Workflow** на весь сценарій, retry з backoff на нодах HTTP і Claude.

## 6. Правило скорингу для `thin` (без ШІ)

Стартова таблиця, під клієнта тюниться:

| Фактор | Бали |
|---|---|
| Канал: referral | 60 |
| Канал: форма сайту (органіка) | 45 |
| Канал: платний трафік | 35 |
| Канал: холодний контакт | 25 |
| Є і телефон, і email | +10 |
| Повторне звернення (touches > 1) | +15 |
| Звернення в робочі години | +5 |

Пороги: 70+ hot · 40-69 warm · <40 cold.

Це свідомо просте і прозоре правило. На дзвінку це сильний аргумент: клієнт бачить, що ШІ поставлений там, де він потрібен, а не всюди.

## 7. Промти (два, обидва вузькі)

**Промт A — thin_comment.** Вхід: текст коментаря + канал. Задача: визначити теплоту і намір. Вихід: score, heat, category, reason. Draft порожній. Категорій три-чотири, не більше.

**Промт B — rich.** Вхід: контакт, компанія, збагачення, текст запиту. Задача: оцінити відповідність профілю ідеального клієнта, пояснити бал одним реченням, написати чернетку відповіді в тоні компанії. Вихід: повний контракт.

Обидва промти: тільки JSON, без преамбули, без markdown-огорожі. Температура 0. У промт вкладається приклад точного формату виходу, у JSON-схему — описи полів.

### Шари захисту виходу

Покладатись на один механізм не можна. Порядок шарів:

1. інструкція формату в системному промті + приклад;
2. Structured Output Parser (схема з прикладу JSON або вручну; `$ref` не підтримується);
3. Auto-Fixing Parser — **з обережністю**, у нього є відомі баги: падіння на потрійних бектиках усередині JSON-рядків і втрата виправленого JSON, коли модель повертає контент блоками;
4. **власний Code-валідатор** — обов'язковий, а не запасний. Чистить огорожу, перевіряє наявність усіх полів контракту, типи і діапазон `score`.

## 8. Надійність

### Політика ретраїв

Ретраїти: 408, 409, 425, 429, 500, 502, 503, 504.
Не ретраїти: 400, 401, 403, 404, 422.
Затримка: `min(maxDelay, baseDelay × 2^(attempt-1))` + випадковий джитер.

**Retry on Fail ставиться тільки на ноди без побічних ефектів** — HTTP-збагачення і виклик Claude. На ноди, які пишуть (Airtable create, Gmail draft), ретрай не вішається: три спроби дадуть три записи або три чернетки. Там — Continue on Error плюс перевірка існування перед записом (у нас це `dedupe_key`).

### Error Workflow

Окремий воркфлоу з Error Trigger, спільний на весь інстанс. Отримує ID воркфлоу, ID виконання і текст помилки, пише рядок у `Runs` і шле сповіщення.

Змінна середовища: `EXECUTIONS_DATA_SAVE_ON_ERROR=all` — щоб дані впалого виконання зберігались і прогін можна було перезапустити з UI.

## 9. Тест-кейси (те, що показуємо у відео)

1. B2C-заявка, тільки телефон, канал referral → правило, 60 балів, warm, автоворонка. ШІ не викликався.
2. B2C-заявка з коментарем «скільки коштує, треба на наступний тиждень» → ШІ, hot, алерт у Telegram.
3. B2B-заявка з корпоративного домену → збагачення, повна кваліфікація, персональна чернетка в Gmail.
4. Повторна заявка з тим самим email → рядок оновився, дубль не створився, touches = 2.
5. Навмисно зламаний API-ключ → воркфлоу не впав, помилка в Runs, сповіщення, needs_review.

## 10. Адаптація під себе (йде в README)

Хто забирає воркфлоу, робить три кроки:

1. **Свій канал.** Підключити свій тригер (Facebook Lead Ads, Instagram DM, WhatsApp, Telegram, своя форма) на вхід ноди `[2] Normalize`. Платформенні дозволи — на стороні того, хто адаптує; воркфлоу їх не вимагає.
2. **Запис у мапі джерел.** Дописати ключ у `SOURCES`: вага каналу і мапінг вхідних полів на канонічний об'єкт. Полів немає — лід стане `thin` і піде правилом, нічого не зламається.
3. **Свої ваги і пороги.** Розділ 6: ваги каналів і пороги 70/40 — це стартові числа, не істина.

Що міняти НЕ треба: контракт виходу, схему Airtable, маршрутизацію, промти.

## 11. Опенсорс: що беремо, що пишемо самі

Правило: дивимось, забираємо ідею або окремий блок, пишемо своє. У свій GitHub іде свій JSON.

### Беремо

| Елемент спеки | Що знайдено | Як використовуємо |
|---|---|---|
| `[3]` + `[7]` Airtable | Нода Airtable має нативну операцію **Create or Update (upsert)**; є шаблон батчевого upsert з `fieldsToMergeOn` | Прибираємо окремий Search + IF, ставимо upsert по `dedupe_key`. Мінус дві ноди |
| `[6]` Валідація | Structured Output Parser (схема з прикладу JSON; `$ref` не підтримується) + шаблон **Robust JSON Parser** (sub-workflow: чистить бектики, лагодить лапки й трейлінг-коми) | Parser як шар 2, Robust JSON Parser як шар 4 замість власного коду з нуля |
| Ретраї | Шаблон reusable retry handler: backoff + джитер + класифікація кодів | Забираємо формулу і списки кодів, не воркфлоу (тягне Slack і SMTP) |
| Error Workflow | Шаблон error logging + alerts (лог у Sheets, лист із назвою воркфлоу, впалою нодою і лінком на виконання) | Структуру рядка логу забираємо, пишемо в Airtable `Runs` замість Sheets |
| `[8]` Gmail draft | Шаблон Gmail AI Auto-Responder: конвертує текст у HTML і кладе чернетку в тред як відповідь на перше повідомлення | Забираємо саме спосіб покласти draft у тред |
| Збагачення | Шаблон enrich company leads через Firecrawl (позиціонується як безкоштовна self-hosted альтернатива Apollo/Clay) | Кандидат, якщо робимо реальне збагачення |

### Пишемо самі

Нормалізація з мапою джерел, rule scoring для `thin`, обидва промти, схема Airtable, маршрутизація за heat, контракт виходу.

### Готчі, які коштують годин

1. **Gmail Trigger «On Message Received» спрацьовує і на створення чернетки.** У нас вхід Gmail і вихід Gmail draft — це готовий нескінченний цикл. Лікується фільтром: query `-in:draft` або виключення лейбла `DRAFT`.
2. **Gmail «Create Draft» не завжди створює справжню відповідь у треді** — відома скарга спільноти навіть при правильно переданому Thread ID. Перевіряти на першому ж тесті.
3. **Auto-Fixing Parser** має два відкриті баги (див. розділ 7). Не покладатись.
4. **Retry on Fail на записуючих нодах** дає дублі записів і листів. Тільки Continue on Error + перевірка існування.
5. **Airtable мовчки ігнорує неіснуюче поле** при створенні запису — помилки не буде, просто не буде даних. Назви полів чутливі до регістру.

### Не знайшов

Безкоштовного API для збагачення B2B-контактів без підводних каменів. У спільноті n8n це відкрите питання. Для демо це не блокер: збагачення можна показати на публічних даних домену або взагалі позначити як опційний крок.

**Ліцензійне правило:** MIT — можна переиспользувати з атрибуцією. Репозиторій без файлу ліцензії — за замовчуванням усі права збережені: дивимось, вчимось, свій код пишемо самі.

### Патерни, які забираємо з LeadIQ-AI

1. **Парсер LLM-виходу** — `JSON.parse` напряму, при падінні regex-витяг `{...}`, далі перевірка обов'язкових полів, enum-валідація пріоритету і звірка score з tier. Це готова заміна нашому шару 4.
2. **Розділення «підготувати рішення» і «виконати»** — окрема нода будує об'єкт маршрутизації (`queue`, `notify_sales`, `send_email`, `archive`) без жодного побічного ефекту, і лише потім ноди виконують. Маршрути — заморожений об'єкт-константа.
3. **Валідація на вході з відповіддю 400** — невалідний запит повертає структуровану помилку, а не падає виконанням.
4. **Перевірка секрету вебхука** окремою нодою перед усім іншим.
5. **Health-check ендпоінт** другим вебхуком — дешево і добре виглядає в кейсі.
6. **Snapshot + Merge після кожного каналу** — статус доставки кожного каналу пишеться окремо, видно, що саме відпрацювало.
7. **`LIMITATIONS.md` у репозиторії** — чесний список обмежень. Сильний хід для портфоліо, копіюємо саму практику.

**Чого з LeadIQ-AI не беремо:** Supabase як залежність для дедуплікації (у нас Airtable upsert) і сам масштаб на 55 нод.
